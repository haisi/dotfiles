X11 + [i3](https://i3wm.org), with [rofi](https://github.com/davatorium/rofi) as the
launcher and `i3status` for the bar. Bindings follow vim-style `hjkl` for focus and
movement, `$mod` is the Super key, and `$mod+r` opens a resize mode.

```
$mod+Return       → open Ghostty
$mod+d            → rofi launcher (combi: window/drun/run)
$mod+Shift+a      → command palette (fuzzy-search keybindings)
$mod+Shift+x      → i3lock
$mod+hjkl         → focus left/down/up/right
$mod+Shift+hjkl   → move the focused window
$mod+1..0         → switch workspace
$mod+r            → resize mode
```

`$launcher` runs `rofi -show combi`, backed by `~/.config/rofi/config.rasi` setting
`combi-modes: "window,drun,run"` — one prompt that searches open windows, applications,
and arbitrary shell commands together, instead of needing separate bindings per mode.

## Command palette

`$mod+Shift+a` runs `i3-command-palette.py`, which parses `~/.config/i3/config` itself
(including `bindsym`/`bindcode` lines nested inside `mode "..." { }` blocks), offers
every binding to rofi as a fuzzy-searchable list, and dispatches the selection over the
i3 IPC socket via `i3-msg`.

The one subtlety: i3 expands `set $name value` variables (`$term`, `$launcher`, ...)
itself while parsing the config file, but a command sent over IPC never goes through
that same parsing pass — so the script has to pre-expand `$`-variables in a binding's
command before handing it to `i3-msg`, or commands referencing them would silently fail.
Bindings can also carry `# @label:` / `# @keywords:` comments directly above them to
override the palette's display text or add extra search terms.

## The keyboard layout race

i3's config sets the layout on startup:

```
exec --no-startup-id setxkbmap ch de_nodeadkeys
```

But `ibus-daemon` starts a second or so after i3 on every login and applies its own
`preload-engines` XKB layout when its first engine activates — which races
`setxkbmap` and silently overrides it back to `us`. Rather than trying to out-race a
timing-dependent startup order, the bootstrap playbook fixes it at the source: it
reads ibus's `preload-engines` gsetting and, if it isn't already
`['xkb:ch:de_nodeadkeys:deu']`, sets it. Once ibus's own preloaded layout is Swiss
German, there's nothing left for it to race `setxkbmap` over.

See [Laptop function keys](/features/laptop-keys/) for the other thing layered onto
this same i3 config — volume/brightness bindings that only appear on laptop hardware.

## Running gnome-control-center under i3

`gnome-control-center` (needed for the Wi-Fi panel, among others) refuses to start
outside GNOME or Unity — it checks `XDG_CURRENT_DESKTOP` for either string and exits
immediately otherwise, which is exactly what i3 sets `XDG_CURRENT_DESKTOP` to. The
check turns out to be cosmetic: `gnome-settings-daemon`'s D-Bus services activate on
demand regardless of desktop, so nothing else about the panels actually depends on
GNOME Shell being present.

`~/.local/bin/gnome-control-center` is a wrapper (`dot_local/bin/`) that re-execs the
real `/usr/bin/gnome-control-center` with `XDG_CURRENT_DESKTOP=GNOME` set only for that
child process — not exported globally, so nothing else that branches on
`XDG_CURRENT_DESKTOP` gets fooled. Since `~/.local/bin` precedes `/usr/bin` on `PATH`,
plain `gnome-control-center` just works.
